[FAQ]

#### Frequently asked questions

Q: How does an engagement start?

With a strategy consultation. If there is a fit, you receive a written proposal and a Statement of Work that fixes scope, deliverables, milestones and acceptance criteria. Many clients begin with a fixed-scope entry offer such as the Cloud & DevOps Health Check.

Q: What contracts do you work under?

Every engagement runs on a written Statement of Work under a master services agreement. A mutual NDA is available before discovery, and a data processing agreement is available on request.

Q: Who owns the work you deliver?

You do. Infrastructure code, pipelines, runbooks and documentation are delivered into your own accounts and repositories, with a full handover and no lock-in.

Q: Do you work in our cloud accounts?

Yes. We work in your accounts and repositories with least-privilege access and MFA, starting read-only wherever possible. Access is reviewed and removed at the end of an engagement.

Q: Can our data stay in a specific region?

Yes. Environments can be designed for the AWS, Azure or Google Cloud regions you choose, including UAE and Saudi Arabia regions where your chosen provider offers them, to support your data-residency requirements.

Q: How do you use AI tools in delivery?

Only under business terms that exclude training on customer data. No client secrets, credentials or personal data are entered into AI tools, every AI-assisted change is reviewed before it reaches your environment, and you can opt out in your SOW.

[Insights]

### A 15-point cloud cost checklist

Fifteen checks for AWS, Azure and Google Cloud estates that find wasted spend quickly, from idle resources and oversized compute to missing budgets and untagged assets.

By Mubashir Ahmed · Founder & Lead Architect · October 15, 2026 · 5 min read

Cloud waste is common, and it is growing again. Flexera’s 2026 State of the Cloud research reports that, after five years of decline, wasted cloud spend on IaaS and PaaS increased to 29%. The usual suspects are not exotic: resources nobody owns, capacity sized for a peak that never comes, and environments that run when nobody is using them.

The fifteen checks below find that waste on AWS, Azure and Google Cloud alike. Work through them in order: visibility first, because you cannot cut what you cannot attribute.

Key takeaways

- Tag and label everything first; untagged spend has no owner and no one to fix it.
- Remove idle and orphaned resources before you resize anything else.
- Right-size from measured utilization, then commit only to the steady baseline.
- Make cost a monthly routine with budgets and alerts, not a one-off clean-up.

#### Visibility

- Tag everything.

  Every resource should carry environment, owner, application and cost-center tags (labels on Google Cloud). On AWS, activate the tags as cost allocation tags so they appear in billing; on Azure, tag inheritance can apply subscription and resource group tags to usage records; on Google Cloud, labels flow into the billing export. Enforce the tags with policy in your

  → Link: landing zone

  , so untagged resources cannot be created.

- Break spend down by environment. If Dev and QA cost almost as much as production, they are probably oversized or running when nobody uses them. Separate accounts, subscriptions or projects per environment make this view trivial.
- Set budgets and alerts. Use AWS Budgets, Azure Cost Management budgets or Google Cloud budgets for each account, subscription or project and for each major application. Send alerts to the people who own the spend, not to a shared mailbox nobody reads, and alert on forecast as well as actual cost.

#### Idle and orphaned resources

- Unattached disks and volumes. Disks left behind after a VM or instance was deleted keep charging. Search for volumes in an unattached state, snapshot them if in doubt, then delete them.
- Unused public IP addresses. All three providers bill for public IPv4 addresses that are not attached to anything: AWS charges for every public IPv4 address, attached or idle; Azure charges for a static public IP whatever it is associated with; Google Cloud charges a higher rate for a reserved static address that is not in use.
- Old snapshots and backups. Keep what your retention policy requires and delete the rest automatically. Snapshot policies without an expiry rule grow forever.
- Forgotten environments. Temporary test or demo environments often outlive their purpose. Give them an expiry tag when they are created and review anything past its date.

#### Right-sizing

- Check compute utilization. VMs, instances and App Service plans running at low average CPU and memory are candidates for a smaller size. AWS Compute Optimizer, Azure Advisor and Google Cloud’s machine type recommendations all suggest sizes from observed usage; treat them as a shortlist to verify, not as instructions.
- Review database tiers. Managed databases are often provisioned for a peak load that never arrives. Look at real CPU, memory, storage and connection usage before the next change window, and plan the change with a tested rollback.
- Use autoscaling. Scale out for demand and back in afterwards, instead of sizing for the busiest moment all the time. Check that scale-in actually happens; a minimum instance count set during an incident and never reverted is a common source of waste.

#### Scheduling

- Stop non-production outside working periods. Dev and QA environments rarely need to run overnight or at weekends. Automated start and stop schedules are one of the quickest savings available, and they need no change to the application. Agree the schedule with the people who use the environments, and give them a simple way to start one on demand.

#### Commitments

- Reservations and savings plans. For steady, predictable workloads, AWS Savings Plans, Azure Reservations and Azure savings plans for compute, or Google Cloud committed use discounts reduce the cost of capacity you would run anyway. Commit only to the baseline you are confident about after right-sizing, not to today’s oversized estate.
- Spot capacity for interruptible work. Batch jobs, build agents and test workloads can often run on AWS Spot Instances, Azure Spot Virtual Machines or Google Cloud Spot VMs at a lower price. The provider can reclaim that capacity at short notice, so use it only for work that can stop and restart safely.

#### Architecture

- Storage tiers and lifecycle rules. Move infrequently accessed data to cooler tiers automatically, and expire data you no longer need, with Amazon S3 lifecycle rules, Azure Blob Storage lifecycle management or Google Cloud Storage Object Lifecycle Management. Check retrieval and early-deletion charges on the colder tiers before you move data that is read often.
- Data transfer. Cross-region and internet egress charges add up. Keep chatty services in the same region, use private connectivity between services where it fits, and put caching or a CDN in front of content that is served repeatedly.

#### Running the checklist

A first pass does not need special tooling. In practice:

- Export the last three months of cost data from AWS Cost Explorer, Azure Cost Management or the Google Cloud billing reports, grouped by service and by tag.
- Sort by cost, not by count. Start with the ten most expensive services or resources; a long tail of small items can wait.
- Give every finding an owner and a decision: delete, resize, schedule, commit or keep with a reason.
- Change one thing at a time in production, and compare the next month’s figures against the baseline you exported.

#### Common mistakes

- Buying commitments before right-sizing. You lock in the waste for the length of the term.
- Deleting without an owner check. An “idle” resource can be a disaster recovery standby. Tags and an owner conversation come before deletion.
- One-off clean-ups. Waste returns if nobody owns the numbers.
- Alerts to nobody. A budget alert that goes to a shared inbox is not a control.

#### Make it continuous

A one-off clean-up helps, but waste returns without ownership. Review spend every month by environment and by application, track the actions you take and their effect, and keep budgets, tags and schedules current as the platform changes. Our Cloud Cost Optimization service runs this review as a structured engagement, and Managed Cloud & DevOps keeps it going as part of the monthly service report.

[Insights]

### Bitbucket branch governance: the restrictions and SOPs every team should have

A practical baseline for Bitbucket branch permissions, merge checks and written SOPs that keeps main deployable without slowing developers down.

By Mubashir Ahmed · Founder & Lead Architect · October 14, 2026 · 6 min read

A repository without branch governance relies on everyone remembering the rules. That works until a busy week, a new team member or a late-night fix. Bitbucket Cloud has the controls to make most of the rules automatic, but some of them only warn rather than block unless you are on the Premium plan, and that difference is easy to miss.

This is the baseline we recommend and set up when we take on repository governance, with a clear note of which controls work on Standard and which need Premium.

Key takeaways

- Start with branch permissions on main: changes only through pull requests, no deletion, no history rewrites.
- Merge checks only warn on Standard. Blocking a merge until they pass needs Bitbucket Cloud Premium.
- Make the pipeline the gatekeeper, and deploy to AWS, Azure or Google Cloud with short-lived OIDC credentials.
- Write short SOPs for the human steps, and review access on a schedule.

#### Standard or Premium: what each control needs

Atlassian lists four controls that the Premium plan adds to Standard: enforced merge checks, deployment permissions, IP allowlisting and required two-step verification. In practice:

| Control | Standard | Premium |
| --- | --- | --- |
| Branch permissions (who can write or merge, no deletion or history rewrite) | Yes | Yes |
| Merge checks: approvals, passing builds, resolved tasks, no requested changes | Shown as warnings; users can still merge | Can block the merge (“Prevent a merge with unresolved merge checks”) |
| Reset approvals when the source branch changes | No | Yes |
| Deployment permissions (which branches can deploy to an environment) | No | Yes |
| IP allowlisting and required two-step verification | No | Yes |

Plans and features change, so confirm against Atlassian’s pricing page before you rely on a specific control.

#### Pick a branching model and write it down

Keep it simple. For most product teams:

- main is always deployable and reflects production.
- develop (optional) collects work for the next release if you need a staging line.
- Short-lived feature/, bugfix/ and hotfix/ branches carry individual changes.
- release/ branches are used only if you ship versioned releases.

Turn on the branching model in the repository settings so the branch prefixes are suggested when people create branches, and so you can apply permissions by branch type. Write the naming convention in the repository README or SOP document as well; settings show what is allowed, but not why.

#### Branch permissions on main

Configure branch permissions so that, on main:

- Nobody pushes directly. Give write access to no one, and merge access through pull requests to the people or groups who are allowed to release.
- No deletion and no history rewrites. History stays intact and the branch cannot disappear by mistake.
- Groups, not individuals. Grant access to workspace groups, so permissions follow roles when people join or leave.

Apply the same permissions to develop and release/* if you use them. These settings work on Standard and are the single most effective step you can take.

#### Merge checks that enforce quality

Merge checks turn review rules into requirements. A good baseline:

- At least one approval, or two for high-risk repositories.
- No unresolved pull request tasks and no outstanding “changes requested”.
- At least one successful build on the last commit, with no failed or in-progress builds.
- On Premium, reset approvals when new commits are pushed, so reviewers always approve what is actually merged.

On Standard, these checks appear as warnings and a developer can still merge. That is still useful, because it makes skipping a check a visible, deliberate act, but it is not a control. If your process requires that nothing reaches main without review and a passing build, you need Premium’s “Prevent a merge with unresolved merge checks”.

#### Code owners and default reviewers

A .bitbucket/CODEOWNERS file adds the right reviewers to a pull request automatically, based on the files it changes: the platform group for pipeline and infrastructure files, the payments group for billing code, and so on. Default reviewers, set in the repository settings, are added to every pull request.

Code owners suggest reviewers; they do not force an approval from them. Combine them with a minimum-approvals merge check, and keep the file short enough that people actually maintain it.

#### Pipelines as the gatekeeper

Bitbucket Pipelines (or your CI tool) should run tests, linting and security scans on every pull request, and the merge check should require that build to pass. We design these pipelines as part of our CI/CD & DevOps Transformation work.

For deployments, use Bitbucket deployment environments (Test, Staging and Production) so every release is recorded against an environment. On Premium, deployment permissions restrict which branches can deploy to Production; on Standard, protect production with branch permissions and a manual trigger step instead.

Avoid long-lived cloud keys in repository variables. Bitbucket Pipelines can issue OpenID Connect (OIDC) tokens, and Atlassian documents the setup for AWS and Google Cloud. Azure accepts the same kind of token through Microsoft Entra workload identity federation. Each deployment then receives short-lived credentials scoped to one environment.

#### Access reviews

Repository permissions accumulate over time. Review workspace and repository access on a regular schedule:

- Remove leavers and accounts that have not been used.
- Downgrade people who no longer need write access.
- Keep admin rights to a small group, and record why each admin has them.
- Check that API tokens, access tokens and SSH or deployment keys still have an owner and a purpose.

On Premium, IP allowlisting and required two-step verification tighten access further.

#### The SOPs that make it stick

Settings enforce rules; SOPs explain them. Every team should have short written procedures for:

- Starting work: branch naming, linking to the ticket, keeping branches short-lived.
- Opening a pull request: description template, screenshots or test evidence, and who should review.
- Reviewing: what reviewers check, and when to request changes rather than approve.
- Releasing: how a merge to main reaches production, and who approves it.
- Hotfixes: the expedited path, which still goes through a pull request and a passing build.
- Access changes: who can grant repository access, and how requests are recorded.

Keep SOPs in the repository or a shared wiki, version them, and update them when the process changes. Repository governance with written SOPs is part of what we run day to day in Managed Cloud & DevOps.

#### Common mistakes

- Assuming merge checks block on Standard. They warn. Check your plan before you write “enforced” in a policy.
- Permissions granted to individuals. They outlive role changes. Grant access to groups and review the groups.
- Approvals that survive new commits. Without the Premium reset, re-request review when a pull request changes substantially.
- Cloud keys in repository variables. Prefer OIDC, and rotate anything that must remain a static secret.
- SOPs nobody reads. Link them from the pull request template, where people actually look.

#### Where to start

Turn on “no direct pushes” on main and add the passing-build and approval merge checks first. They close the most direct routes to an untested change, even as warnings. Add code owners, deployment environments and access reviews next, decide whether your process needs Premium’s enforcement, then write the SOPs that describe how your team works today.

[Insights]

### Dev, QA, UAT, Prod on Azure: an environment strategy that survives real releases

How to structure Azure environments so code moves predictably from a developer's branch to production, with parity, isolation and controlled promotion at every step.

By Mubashir Ahmed · Founder & Lead Architect · October 12, 2026 · 7 min read

Most release problems are not code problems. They are environment problems: a setting that exists in QA but not in production, a database that drifted, a hotfix that skipped testing because UAT was “busy”. None of these is solved by writing better code. They are solved by deciding what each environment is for, building every environment the same way, and moving one tested build through them in a fixed order.

This article sets out the approach we use on Azure, the mistakes we see most often, and how the same ideas carry over to AWS and Google Cloud.

Key takeaways

- Give each environment one job, and isolate production in its own subscription.
- Build every environment from the same Infrastructure as Code modules, with only parameters changing.
- Build once and promote the same artifact from Dev to production, ending with a slot swap behind an approval.
- Keep secrets in one Key Vault per application and environment, read through managed identities.

#### Four environments, four jobs

Each environment should exist for one reason, and everyone should know what that reason is.

- Dev is where integrated work lands first. It changes constantly and is allowed to break.
- QA is where automated and manual tests run against a known build. Nothing is deployed to QA by hand.
- UAT is where business users confirm that the release does what they asked for. It should look and behave like production, with realistic (masked) data.
- Prod serves customers. Changes reach it only by promoting a build that has already passed QA and UAT.

If two environments do the same job, merge them. If one environment is doing two jobs, split it. A common example is a “staging” environment used both for testing and for sales demonstrations: testers need to break it, and the demo needs it stable. Those are two jobs.

#### Isolation: subscriptions first, resource groups second

At minimum, give each environment its own resource group. For anything handling sensitive or customer data, give production its own subscription, and put the non-production environments in a second one. A subscription is a much stronger boundary than a resource group: role assignments, policies, quotas and budgets can all be scoped to a subscription, so a broad role granted in Dev cannot reach production by accident, and cost reporting per environment becomes straightforward.

Group the subscriptions under management groups (for example one for production and one for non-production) so that policies are assigned once and inherited, rather than repeated on every subscription.

#### Naming and tagging

Name everything consistently, for example rg-<app>-<env>-<region> for resource groups and kv-<app>-<env> for vaults, and tag every resource with environment, owner, application and cost center. Do not rely on people remembering: Azure Policy can require a tag, add a missing tag, or inherit it from the resource group, so untagged resources never appear in the first place.

Tags pay for themselves the first time someone asks what a resource is for, or why a bill went up.

#### Parity through Infrastructure as Code

Environments drift when they are built by hand. Define every environment with the same Terraform or Bicep modules, and pass in only the differences (SKU sizes, instance counts, network ranges, alert thresholds) as parameters, one file per environment:

- infra/modules/: the App Service, database, Key Vault and monitoring modules, shared by every environment.
- infra/env/dev.bicepparam, qa.bicepparam, uat.bicepparam and prod.bicepparam: one parameter file per environment, holding only the differences.

If a resource exists in production, the same code should be able to create it in Dev. Run the plan or what-if step in the pipeline on every change, and treat a manual change in the portal as an incident to be written back into code. Our Infrastructure as Code & Landing Zones work starts exactly here.

#### Configuration and secrets per environment

Keep configuration out of the code and out of the build. Store non-secret settings in App Service configuration or Azure App Configuration, and store secrets in Key Vault. Microsoft’s own guidance is to use one Key Vault per application, region and environment, so that a leaked Dev credential can never open the production vault.

Applications should read secrets through managed identities, so no connection strings live in pipelines, repositories or developers’ machines. In App Service, mark environment-specific settings as deployment slot settings, so they stay with the slot and do not travel during a swap.

A useful rule: if copying a production setting into Dev would be dangerous, it belongs in Key Vault.

#### Promotion, not redeployment

Build once and promote the same artifact through every environment. The pipeline should:

- Build and test on every pull request.
- Deploy the merged build automatically to Dev.
- Promote that same build to QA when Dev checks pass.
- Promote to UAT after QA sign-off.
- Promote to production through an approval gate, ideally via a slot swap.

Rebuilding for each environment means production runs code that was never tested. Promoting one artifact, identified by its version or commit, removes that risk. In Azure Pipelines, model each stage as an environment with approvals and checks; GitHub Actions environments with protection rules do the same job. We design and build these pipelines in our CI/CD & DevOps Transformation service.

#### Slot swaps for production releases

App Service deployment slots (Standard, Premium and Isolated tiers) let you deploy the release to a staging slot, check it, and swap it into production. App Service warms up the instances in the staging slot before the swap, so users do not hit a cold start, and if something goes wrong you swap the same two slots again to get the previous version back.

Two details matter. Database changes must be backwards compatible, because after a swap back the old code runs against the new schema. And anything slot-specific, such as a connection string to a staging dependency, must be marked as a slot setting.

#### Data: realistic, but never real

UAT is only useful if its data looks real. Refresh it from production on a schedule, with personal data masked or replaced during the copy, and make the masking step part of the refresh pipeline rather than a manual task. Never point lower environments at production databases, even read-only.

#### Hotfixes without shortcuts

Hotfixes are where strategies usually break. Give them a defined path: a hotfix branch, the same pipeline, a short QA check and an expedited approval. The process can be faster than a normal release, but it should never skip environments entirely, and the fix must be merged back to the main branch so the next release does not undo it.

#### Common mistakes

- One subscription for everything. It works until someone with Contributor rights in Dev runs a script against the wrong resource group.
- A shared Key Vault. One vault for all environments means every environment can read production secrets.
- Rebuilding per environment. Different builds in QA and production make QA results meaningless.
- UAT that nobody refreshes. Stale data hides bugs until production.
- Portal fixes that never reach code. The next deployment silently reverts them.

#### Where to start

If your environments have grown organically, start by writing down what each one is for, then bring the most critical one (usually production) under Infrastructure as Code. Parity follows once every environment is built from the same modules. If you would rather have the platform run for you day to day, that is what Managed Cloud & DevOps covers.

#### On AWS or Google Cloud?

The same ideas apply on the other two clouds; only the names change.

| Idea | Azure | AWS | Google Cloud |
| --- | --- | --- | --- |
| Environment boundary | Subscription | Account | Project |
| Grouping and policy | Management groups, Azure Policy | AWS Organizations, organizational units, service control policies | Folders, Organization Policy |
| Infrastructure as Code | Bicep or Terraform | CloudFormation, AWS CDK or Terraform | Terraform (also through Infrastructure Manager) |
| Secrets | Key Vault | AWS Secrets Manager | Secret Manager |
| Workload identity | Managed identities | IAM roles | Service accounts |
| Staged release with quick rollback | App Service slot swap | Blue/green deployment (for example Amazon ECS with CodeDeploy) | Cloud Run revisions with traffic splitting |

On AWS, use separate accounts for production and non-production, grouped into organizational units. On Google Cloud, use a project per environment, grouped under folders. The rules stay the same everywhere: one job per environment, one set of modules, one promoted artifact.

#### SOP: Source control and branch governance

Owner: Engineering lead · Applies to: all repositories in the workspace · Review: whenever the process changes

##### 1. Branches

| Branch | Purpose | Rules |
| --- | --- | --- |
| main | Production-ready code | No direct pushes, no force pushes, no deletion |
| develop (optional) | Next release integration | Same restrictions as main |
| feature/<ticket>-<short-name> | New work | Short-lived; deleted after merge |
| bugfix/<ticket>-<short-name> | Non-urgent fixes | Short-lived; deleted after merge |
| hotfix/<ticket>-<short-name> | Urgent production fixes | Follows section 5 |

##### 2. Starting work

- Create a branch from the correct base using the naming convention above.
- Reference the ticket in the branch name and in commit messages.
- Keep the branch focused on one change and merge it as soon as it is ready.

##### 3. Pull requests

- Open a pull request into the target branch using the PR description template.
- Include what changed, why, how it was tested, and any deployment notes.
- The pipeline must pass on the latest commit before review is requested.

##### 4. Review and merge

- Approvals required: at least one, or two for repositories marked critical.
- Merge checks: no unresolved tasks, a passing build, approvals reset on new commits (Bitbucket Premium).
- Reviewers check: correctness, tests, security impact, configuration changes and documentation.
- Merge strategy: squash merge for feature branches, unless the repository specifies otherwise.

##### 5. Hotfixes

- Branch hotfix/... from main.
- Open a pull request with the incident reference.
- The pipeline must pass; one approval from a release owner is required.
- After release, merge the fix back into develop if it is in use.

##### 6. Releases

- A merge to main triggers the release pipeline.
- Production deployment requires approval from a named release owner.
- Release notes are generated from merged pull requests.

##### 7. Access management

- Access is granted to groups, not individuals.
- Write access requests are approved by the engineering lead and recorded.
- Admin rights are limited to a small named group.
- Access is reviewed regularly; leavers are removed on their last day.

##### 8. Exceptions

Any exception to this SOP is approved by the engineering lead, recorded with a reason, and reviewed afterwards.
